§1 Initial request

We would like to generate a fix report and save it in our 'waves' directory. For this we will use a folder name of the format fix-{slug}. This feature update should be recorded in our documentation.

§4 Features

Each card below is one Feature. Acceptance criteria are numbered so QA can map a failing test to each numbered item.

F1

/stx-fix writes a per-fix folder with fix-report.html and fix-state.json

todo
Actor: developer running /stx-fix against a reproducible bug

Acceptance criteria

  1. Running /stx-fix to completion against a known bug creates a directory at docs/waves/fix-{slug}/ where {slug} is derived from the bug title (kebab-case, same slug rule already used by /stx-fix for branch naming).
  2. The folder name is literally fix-{slug} (no random suffix, no timestamp suffix). If a folder with the same slug already exists, the orchestrator surfaces this rather than silently overwriting — the chosen collision-handling strategy is an Architect decision but the chosen behavior MUST be documented in stx-fix/SKILL.md.
  3. Inside docs/waves/fix-{slug}/, exactly two files are written: fix-state.json (canonical machine-readable state for that fix run) and fix-report.html (rendered human-readable report). No prompt snapshot file is written.
  4. fix-state.json contains at minimum: a fix_id, fix_slug, status (one of done | halted-at-cap | blocked | cancelled), started_at, finished_at, the rendered template fields (title, issues, repro, expected, scope_hints, out_of_scope, test_kind, iteration_cap, commit_policy), the iteration count actually consumed, and references to the failing test files written by QA and the production files touched by Coder.
  5. fix-report.html is self-contained (offline-renderable, inline styles) and visually consistent with the existing /stx-feature wave artifacts (reuses _styles.html-equivalent typography, colors, card and status conventions).
  6. Both files are written before /stx-fix's existing terminal summary is printed.
  7. The last line of the terminal summary printed by /stx-fix is Report written to <abs-path-to-fix-report.html> (the existing in-conversation terminal summary is otherwise preserved unchanged).
  8. Halt paths (iteration cap tripped, Coder edits a test file, user cancels at the acceptance gate before Step 6, etc.) still write fix-state.json with the appropriate non-done status, and a fix-report.html that reflects the halted state. The orchestrator never silently skips the artifact write.
  9. The new behavior is default — no flag is required to turn it on, and no flag turns it off.

Existing system impact

Touches .claude/skills/stx-fix/SKILL.md (Step 7 "Done or halted" must now also describe writing the per-fix folder; Step 6 may need a note about when state is flushed to disk), .claude/skills/stx-fix/template.md (the rendered §9 "Reporting back to the user" section needs to include the artifact write + the new last-line of the terminal summary), and .claude/skills/stx-fix/catalog.json (artifacts produced, version bump).

The QA and Coder personas at .claude/agents/stx-qa.md and .claude/agents/stx-coder.md may need to surface the list of files they wrote/touched back to the orchestrator in a structured form (today they report freeform). This is required so fix-state.json can record the failing test paths and the production files touched. The Architect should decide whether to extend the persona reporting contract or scrape it from existing freeform output.

Introduces a new file-shape convention under docs/waves/: until now this directory has held only wave-*/ folders written by /stx-feature plus the wave-wiki.html aggregator. Adding fix-*/ folders is a new sibling shape — orchestration code that scans docs/waves/*/ (notably the wave-wiki rebuild) needs to be aware of the new shape. (F2 handles the scan-tightening side of this.)

The fix-report renderer is new code. Whether it lives under src/skills/ as a TypeScript module, as a templated string inside SKILL.md, or as a shared template in .claude/skills/stx-fix/templates/ mirroring the /stx-feature layout is an Architect decision — but it MUST exist as a discoverable artifact in the repo so the build pipeline and tests can reach it.

Out of scope (specific to this Feature)

  • Adding a random-suffix or timestamp-suffix to the fix folder name — the name is literally fix-{slug}.
  • Adding a --report or --no-report flag to /stx-fix — the artifact write is unconditional.
  • Writing a prompt-snapshot file inside fix-{slug}/ — only fix-report.html and fix-state.json are written.
  • Changing the QA → Coder loop semantics, the iteration caps, or any halt conditions.
  • Changing the Coder's prohibition on editing test files, or the QA/Coder separation rule.
  • Mid-loop streaming of fix-report.html as a live dashboard — the report is written at fix-end (or halt), not per-iteration. (If the Architect chooses to also flush state mid-loop for crash recovery, that's an implementation detail, not an acceptance criterion of this Feature.)
  • Cross-fix aggregation — that is F2.
  • Help-doc regeneration — that is F3.
F2

fix-wiki.html cross-fix index (sibling of wave-wiki.html)

todo
Actor: developer browsing docs/waves/ to see all past fixes at a glance

Acceptance criteria

  1. After /stx-fix completes (done or halted) and writes its per-fix folder per F1, a separate aggregator file at docs/waves/fix-wiki.html is rebuilt from scratch by scanning every docs/waves/fix-*/fix-state.json.
  2. fix-wiki.html visually mirrors the existing docs/waves/wave-wiki.html — same header eyebrow + serif H1, same INLINE_STYLES block from _styles.html, same single-table layout sorted by started_at DESC, same status pill classes.
  3. The fix-wiki table includes one row per fix-*/ folder regardless of status (done | halted-at-cap | blocked | cancelled) so the table doubles as a live dashboard.
  4. Each row in fix-wiki.html links to the corresponding ./fix-{slug}/fix-report.html (or ./fix-{slug}/ if the report file is missing).
  5. fix-wiki.html is idempotent: deleting a fix-*/ folder and re-running any /stx-fix removes that row; manually creating a fix-*/ folder with a valid fix-state.json adds a row. The file is never hand-edited and never appended-to in place.
  6. The existing wave-wiki.html scan is tightened so it only picks up wave-*/ folders (matching pattern wave-<slug>-<4-char-suffix>/wave-state.json). fix-*/ folders must NOT appear as rows in wave-wiki.html, and wave-*/ folders must NOT appear as rows in fix-wiki.html.
  7. fix-wiki.html and the wave-wiki.html scan-tightening are part of /stx-fix's close-out — they do NOT require also re-running /stx-feature.
  8. Header copy on fix-wiki.html is distinct from wave-wiki.html so a casual reader can tell them apart at a glance (e.g. eyebrow says "Cross-fix index · rebuilt on every fix close-out", H1 says "Fix Wiki", and the lede paragraph references /stx-fix not /stx-feature).

Existing system impact

Adds a new template at .claude/skills/stx-feature/templates/fix-wiki.html (or a parallel location the Architect chooses — but the existing /stx-feature templates folder is the obvious sibling) plus a renderer that scans docs/waves/fix-*/fix-state.json. The Architect should decide whether to share the wiki-rendering code path with the existing wave-wiki renderer or duplicate it; the templates are clearly meant to be siblings.

Modifies the wave-wiki rebuild logic to tighten its scan glob: today the comment block in .claude/skills/stx-feature/templates/wave-wiki.html says it scans docs/waves/*/wave-state.json, which is incidentally narrow (it requires the per-wave file to be named wave-state.json). Per Q3 the scan must be tightened so even folders that did happen to ship a wave-state.json by mistake are excluded if they match fix-*/, and the documented glob in the template comment must be updated accordingly.

Adds a new sibling artifact docs/waves/fix-wiki.html. This is the first file (besides wave-wiki.html) that lives at the docs/waves/ root rather than inside a per-run folder. Any tooling that assumes docs/waves/ contains only directories (none today, but worth verifying) is in scope to update.

Out of scope (specific to this Feature)

  • Extending wave-wiki.html to also list fix-*/ folders — the user explicitly chose two separate wikis.
  • Adding a combined cross-everything-in-docs/waves wiki.
  • Adding filters, search, or sort controls to either wiki — both stay as plain HTML tables.
  • Changing the visual look of wave-wiki.html beyond the scan-glob tightening.
  • Adding a feed (RSS / JSON) or an API for cross-fix data.
