§1 Frozen out-of-scope (wave-level)

After Gate 2 closes, anything below is off-limits. Dev agents may NOT touch these areas regardless of how convenient a "while I'm here" change would be. Violations are logged to suspicious[] in wave-state.json.
  • Random-suffix or timestamp-suffix on the fix folder name — the name is literally fix-{slug}/.
  • A --report / --no-report flag on /stx-fix — artifact write is unconditional.
  • A prompt-snapshot file inside fix-{slug}/ — exactly two files (fix-report.html, fix-state.json).
  • Changes to the QA → Coder loop semantics, iteration caps, halt conditions, or the Coder's test-file prohibition.
  • Mid-loop streaming of fix-report.html as a live dashboard. Write at fix-end (or halt).
  • Extending wave-wiki.html to include fix-*/ rows. fix-wiki.html is a separate sibling.
  • Filters, search, sort controls, RSS feeds, or APIs on either wiki.
  • Any change to the repo-root README.md.
  • Any change to the wave-template-doc-prose beyond the bare minimum F2-T4 requires.
  • Hand-editing the BEGIN AUTO / END AUTO regions of generated files.
  • Bumping any other skill's version beyond stx-fix (and its two persona files, which get additive bumps in F1-T3 / F1-T4).
  • Bumping the repo-root package.json version — see Architect decision Q6 below.

§2 Architect decisions on open questions

The Analyst surfaced 6 implementation questions. The Architect resolved each from existing patterns + best judgment. The answers below freeze the implementation direction for the wave.

Q1

Collision handling when docs/waves/fix-{slug}/ already exists

Decision: Halt + AskUserQuestion with three options: (a) overwrite the existing folder, (b) append a numeric suffix -2, -3, … (the suffixed name is a one-off escape hatch, NOT the default name shape), (c) cancel and write nothing. Default option: cancel.

Why: matches the worktree-on-main decision tree in .claude/skills/stx-fix/SKILL.md:80-82 — a three-options-with-defaults pattern the user has already seen and approved. Silent overwrite violates the data-protection rule in ~/.claude/CLAUDE.md; auto-suffixing violates F1's "literally fix-{slug}" rule. The cancel default is the safest behaviour for a fix that's about to overwrite history.

Q2

Persona reporting contract: structured fields vs. scraping freeform output

Decision: Extend stx-qa.md and stx-coder.md (additive minor bump 1.0.0 → 1.1.0 on both) to require a structured hand-back block at the bottom of every report. QA emits tests_written: [path, ...]; Coder emits files_touched: [{path, add, del}, ...]. The existing freeform fields stay; the structured block is appended.

Why: scraping freeform output is fragile — the agents are LLMs and their prose shape drifts. A structured trailer is two extra lines per hand-back and lets the orchestrator parse the values directly into fix-state.json. This mirrors the well-defined hand-back shape that stx-dev-base already uses in the /stx-feature wave (every Dev produces a path-line list at hand-back). F1-T3 and F1-T4 implement.

Q3

Renderer location: TypeScript module, embedded string, or sibling template directory

Decision: Templates live at .claude/skills/stx-fix/templates/fix-report.html and .claude/skills/stx-fix/templates/fix-wiki.html, mirroring .claude/skills/stx-feature/templates/ exactly. The orchestrator (the LLM running /stx-fix) renders by reading the template and substituting placeholders inline — same pattern /stx-feature already uses for result.html and wave-wiki.html. No new TypeScript module under src/skills/.

Why: consistency. /stx-feature renders four HTML artifacts (requirement-verse, architecture-verse, qa-verse, result) by reading .claude/skills/stx-feature/templates/*.html and substituting placeholders — there is no TypeScript renderer for any of them. A TS module for /stx-fix would be a different abstraction in the same repo for the same shape of work. The Markdown / JSON / HTML-template trio is the project's established skill-authoring surface (see CLAUDE.md). Also: a TS module would force a package.json bump (Q6) for net-zero capability.

Q4

State-flush timing: only at fix-end, or also per-iteration

Decision: Write fix-state.json ONCE — at fix-end (status done) or at halt (status halted-at-cap / blocked / cancelled). No per-iteration flush. The orchestrator holds the in-progress state in memory.

Why: matches wave-state.json's lifecycle in /stx-feature — wave-state is the canonical model that is written at gate boundaries and at wave end, not per-iteration. Mid-loop flushing adds complexity (atomic-write needed, schema must tolerate every partial state) for a capability the user explicitly placed out-of-scope: "Mid-loop streaming of fix-report.html as a live dashboard." If a crash recovery becomes important later, that's a separate Feature.

Q5

Wiki-render code sharing: extract a helper, or duplicate

Decision: Neither — there is no code path to share. Both wave-wiki and fix-wiki are rendered by the orchestrator (the LLM) inline by reading their template files. The "tightening" of the wave-wiki scan glob is a one-line documentation update inside .claude/skills/stx-feature/templates/wave-wiki.html's comment block + the matching one-line update in .claude/skills/stx-feature/SKILL.md Step 3 sub-bullet and template.md's rebuild description. No code extraction is possible because there is no code.

Why: the original Analyst question presumed a TypeScript renderer existed. git grep confirms otherwise — src/cli/generate-help.ts is the only generator in the repo, and it's for /stx-help (not waves). The wave-wiki render is performed by the LLM. F2-T2 changes the scan-glob documentation; F2-T4 propagates the same change to the orchestrator instructions in stx-feature/SKILL.md + template.md.

Q6

package.json bump: needed or not

Decision: No bump. This wave touches no code under src/. Per CLAUDE.md's versioning section: "Bump the package version when the installer, generator, or shipped CLIs change." None of those change here. The repo-root package.json stays at 1.10.1.

Why: a consequence of Q3 (no new TS code) and Q5 (no code extraction). The skill version (stx-fix) bumps 1.2.0 → 1.3.0 in F3-T1 / F3-T2 — that's the right granularity for a behaviour change inside one skill. The package version is for the installer/CLI surface, which is unchanged.
